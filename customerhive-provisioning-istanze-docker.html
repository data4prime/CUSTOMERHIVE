schema · architettura (control plane / gateway / data plane) rev. 2026-10-08
Control plane (privato) Gateway (dentro il Data Plane, pubblico minimale) Proxy / TLS Istanze (workload) Infrastruttura / attori esterni

Il Gateway non è una macchina a sé: è un container in più sul Data Plane, instradato da Traefik esattamente come le istanze. Il Data Plane era già l'unica macchina esposta pubblicamente e senza chiavi permanenti, il profilo giusto per ospitarlo.

Responsabilità per attore

Control Plane

Chive CP · privato, nessun listener pubblico

  • Gestione licenze (Managed: scadenza esplicita, rinnovo, revoca all'eliminazione)
  • Gestione istanze esistenti
  • Creazione di nuove istanze
  • Email al referente col link per impostare la password (e «Reinvia link»)

Gateway

Pubblico · minimale, nessuna chiave

  • Riceve i check-in delle istanze (managed e self-hosted)
  • Riceve il webhook della pipeline CI
  • Riceverà anche le richieste demo pubbliche (futuro)
  • Inoltra al Control Plane su canale privato

Traefik

Container Docker, sul Data Plane

  • Instrada il traffico per dominio via label
  • Emette TLS automaticamente

Istanze

Dev, staging, cliente/demo

  • Quattro container per istanza: db, app, scheduler, worker
  • Stessa immagine per app, scheduler e worker
  • Stesso meccanismo per tutte

CI/CD + registry

Pipeline esterna

  • Build dell'immagine versionata
  • Pubblicazione sul registry (Docker Hub privato)
schema · funzionalità del control plane rev. 2026-10-08
Amministrazione (Filament) Licensing (già esistente) Orchestrazione istanze (nuovo) Endpoint esterni (nuovo)

Il dump del database e l'archivio di storage arrivano dal Data Plane via SSH e vengono cifrati subito lato Control Plane, prima di toccare qualunque disco — non restano mai, nemmeno temporaneamente, sul Data Plane. La copia offsite riceve solo i file già cifrati, sempre in coppia. Per ogni istanza Managed Chive CP crea anche la licenza (con scadenza esplicita e controllo dell'IP disattivato), la rinnova su richiesta e la revoca quando l'istanza viene eliminata; il link per impostare la password lo spedisce al referente con la propria posta, anche quando si preme «Reinvia link». Nessun listener pubblico: anche il webhook CI passa dal Gateway, non arriva diretto. "Data Plane" e "Gateway" qui sotto sono due canali distinti (SSH per Docker/dump, HTTPS per il check-in) verso la stessa macchina fisica — il Gateway gira lì come container, non su un server a parte.

schema · funzionalità del gateway rev. 2026-09-17
Gateway (contenitore, pubblico) Funzioni interne / Control Plane

Il Gateway gira come container sul Data Plane, instradato da Traefik — non una terza macchina: il Data Plane era già l'unica esposta pubblicamente e senza chiavi permanenti. Il "canale privato" verso il Control Plane in fondo a questo schema è quindi l'unico salto che attraversa davvero una rete tra macchine diverse. Scritto in Slim (PHP) invece di Laravel: stesso linguaggio del resto dello stack, ma un nucleo molto più piccolo — solo routing e gestione richieste, niente ORM/code/sessioni installati per forza. Per un componente con due sole rotte reali, meno dipendenze da tenere aggiornate e nessuna vulnerabilità di Laravel/Chive CP che si ripercuote automaticamente qui. Se il Control Plane non risponde in tempo, il Gateway restituisce un errore chiaro al chiamante invece di restare appeso. Cosa significa "nessuna cache di riserva": il Gateway potrebbe tenere una copia recente degli esiti di validazione, per rispondere comunque a un check-in anche se il Control Plane fosse irraggiungibile per un momento — abbiamo scelto di non farlo nella v1: un check-in fallito è solo un errore temporaneo (il prossimo, un'ora dopo, riprova), mentre una cache sarebbe un'altra copia di dati da tenere sincronizzata e protetta anche sul Gateway — esattamente il tipo di stato in più che vogliamo evitargli.

Un terzo relay è già previsto ma non ancora costruito: quando esisterà la richiesta demo pubblica (vedi "Chi avvia la creazione di un'istanza"), sarà il Gateway a riceverla dalla landing page e a inoltrarla al Control Plane — stessa logica dei due relay qui sopra, nessun meccanismo nuovo da progettare.

Tutti gli endpoint del Gateway, con i body reali che viaggiano in richiesta e risposta.

POST /api/api-license/license-server/auth/login — chi chiama: l'istanza stessa, al check-in e a ogni login di un utente. Il prefisso /api/api-license è quello che il codice dell'app ha già scritto dentro (e che usano anche i clienti di oggi): il Gateway deve rispondere esattamente su questi percorsi, non su una versione accorciata. Nelle note successive li abbrevio con ….

// richiesta (header: x-host, x-host-name con l'URL e il nome dell'app)
{
  "license_key": "a1b2c3d4-e5f6-7890-abcd-ef1234567890",
  "ls_domain": "acme-corp.thecustomerhive.com"
}

// risposta (200) — busta fissa { success, message, data }
{
  "success": true,
  "message": "Successfully logged in.",
  "data": { "access_token": "xY9kLp3mZqRt7vWn2sHj8cBf..." }
}

// risposta (401 — chiave/dominio sbagliati, oppure IP non consentito)
{ "success": false, "message": "Invalid license key or license source." }

POST …/license-server/license — chi chiama: l'istanza, subito dopo aver ottenuto il token. Header Authorization: Bearer <token> più gli stessi header di sopra; nel corpo la chiave e il dominio.

// richiesta
{
  "license_key": "a1b2c3d4-e5f6-7890-abcd-ef1234567890",
  "domain": "acme-corp.thecustomerhive.com"
}

// risposta (200) — l'app salva "data" in storage/app/license.json
{
  "success": true,
  "data": {
    "id": 42,
    "domain": "acme-corp.thecustomerhive.com",
    "license_key": "a1b2c3d4-e5f6-7890-abcd-ef1234567890",
    "path": "acme-corp",
    "status": "active",
    "expiration_date": "2027-10-08T15:45:17.000000Z",
    "expires_in": 364,
    "is_trial": false,
    "is_lifetime": false,
    "tenants_number": 3,
    "clients_number": 50,
    "created_at": "2026-10-08T15:45:17.000000Z",
    "updated_at": "2026-10-08T15:45:17.000000Z",
    "deleted_at": null,
    "modules": [
      { "id": 7, "name": "Qlik", "pivot": { "license_id": 42, "module_id": 1 } }
    ]
  }
}

I campi qui sopra sono quelli che l'app legge davvero (id, domain, path, status, i limiti di tenant e utenti, i modules); il corpo qui sopra è la risposta reale del server di licenza, misurata in locale (le date sono in formato ISO 8601 UTC, expires_in sono giorni interi, modules è un elenco di oggetti e non di semplici nomi). Un dettaglio utile: un login con licenza scaduta riesce comunque — il server la marca inactive ed emette il token — ed è l'app a leggere lo stato dalla risposta di questa chiamata e a bloccare l'accesso, senza perdere la chiave: dopo il rinnovo il login torna a funzionare da solo (corretto in LICENSES e CustomerHive, docs 014 e 301). Il file license.json contiene anche la license_key in chiaro (sta nel volume storage). Il domain salvato nella licenza è l'host completo dell'istanza (il server di licenza ha i sottodomini abilitati), quindi coincide con il APP_DOMAIN dell'istanza. Il controllo dell'IP: il server di licenza lega la licenza al primo IP da cui la vede. Passando dal Gateway vedrebbe sempre l'IP del Gateway e non quello dell'istanza: se il Gateway o il Data Plane cambiano IP, tutte le licenze risponderebbero "IP non consentito" insieme. Per questo le licenze Managed vengono create con questo controllo disattivato (un flag sulla licenza, che Chive CP imposta alla creazione); per tutte le altre resta attivo come oggi.

POST /ci/webhook — chi chiama: la pipeline CI, non un'istanza.

// richiesta (ramo dev)
{ "tag": "dev-a1b2c3d", "branch": "dev" }

// richiesta (ramo release)
{ "tag": "v1.4.0", "branch": "release" }

// risposta (202 — l'azione vera avviene dentro Chive CP, non nella risposta)
{ "received": true }

GET /health — chi chiama: un sistema di monitoraggio esterno. Nessun corpo in ingresso, nessuna autenticazione — non inoltra nulla a Chive CP, verifica solo che il processo del Gateway sia vivo.

// risposta (200)
{ "status": "ok" }

POST /demo-request — futuro, non ancora costruito. Chi chiamerà: il modulo "Preparami una demo" sulla landing page.

// richiesta
{
  "company": "Acme Corp",
  "email": "mario.rossi@acmecorp.it"
}

// risposta (200)
{ "message": "Richiesta ricevuta, ti contatteremo a breve." }
schema · funzionalità del data plane rev. 2026-10-08
Traefik Istanze Gateway Attori esterni

Ogni istanza è un gruppo di quattro container: db, app, scheduler e worker. App, scheduler e worker usano la stessa immagine e cambia solo il comando; scheduler e worker sono sempre accesi e partono solo quando l'app è healthy. Il gruppo sta sulla propria rete Docker privata; solo il container app si aggancia anche alla rete condivisa con Traefik, che punta solo a lui (porta 8080) — il DB, lo scheduler e il worker non sono mai raggiungibili dall'esterno né da un'altra istanza. Il Gateway è un container in più sulla stessa macchina, instradato dallo stesso Traefik: il check-in da un'istanza verso il Gateway è una chiamata interna al Data Plane, non un salto di rete verso un'altra macchina. Nessuna porta oltre 80/443/22 è esposta sull'host. Provato in locale (Chive CP, LICENSES 016): le etichette generate funzionano con Traefik v3.6 o successivo (la 3.1 non parla con Docker 29), TRUSTED_PROXIES con il CIDR reale della rete Traefik fa uscire i redirect e i link in https; Let's Encrypt e l'IP reale del client vanno ancora verificati su un host Linux. Tutto quello che l'immagine si aspetta da Chive CP è nella sezione successiva.

schema · il contratto dell'immagine rev. 2026-10-08

Cosa l'immagine si aspetta da Chive CP: Chive CP genera docker-compose.yml e .env di ogni istanza rispettando questa tabella.

VoceContenuto
ImmagineUna sola, su un repository privato di Docker Hub: tag dev-latest, dev-<sha>, vX.Y.Z. APP_VERSION la imposta il build, non il .env.
Servizio appApache, porta 8080, come www-data. L'unico che esegue le migrazioni (all'avvio) e l'unico con healthcheck. Nell'immagine non c'è tinker (dipendenza di sviluppo): per la diagnosi si usano i comandi php artisan o uno script PHP che avvia l'applicazione.
Servizio schedulerphp artisan schedule:work — scadenza utenti, avvisi, rinfresco orario della licenza, pulizia MFA. Orari secondo app.timezone = Europe/Rome, non l'ora UTC del container.
Servizio workerphp artisan queue:work qlik_sync --queue=qlik_sync,mail --sleep=3 --tries=1 --timeout=3600 — sync Qlik ed email in coda (avvisi di scadenza, email ritardate). Attenzione: il primo argomento di queue:work è la connessione (qlik_sync), le code si elencano con --queue; la forma queue:work qlik_sync,mail non parte.
Servizio dbMySQL con credenziali per istanza; dati nel volume db-data. Le credenziali di root stanno in un file db.env separato, letto solo dal servizio db: app, scheduler e worker leggono il .env applicativo, che non contiene MYSQL_ROOT_PASSWORD (l'app si collega solo con l'utente dell'istanza).
AvvioScheduler e worker sempre accesi in ogni istanza; depends_on con condition: service_healthy sull'app. Su entrambi stop_signal: SIGTERM (senza, docker stop manda SIGWINCH, che ignorano: exit 137 dopo il timeout). Healthcheck dell'app con start_period: 240s.
Porta e healthcheckL'etichetta Traefik punta a 8080. L'healthcheck sta nel compose, solo su app (php chiama http://127.0.0.1:8080/health; nell'immagine non c'è curl): nell'immagine lo erediterebbero scheduler e worker.
Variabili: app e databaseAPP_KEY (per istanza), APP_URL, APP_DOMAIN (host completo <slug>.<dominio base>), APP_PATH (= slug), APP_ENV=production, APP_DEBUG=false, DB_* (credenziali per istanza).
Variabili: code e licenzaQUEUE_DRIVER=database, MAIL_QUEUE_CONNECTION=mail, CUSTOM_CONTROLLERS_PATH=storage/app/custom-controllers, LICENSE_SERVER_URL (il Gateway). La chiave di licenza non sta nel .env delle istanze Managed.
Variabili: log e reteLOG_CHANNEL=stderr (altrimenti i log vanno in un file dentro storage e docker logs è vuoto), TRUSTED_PROXIES (Traefik; le reti delle istanze sono isolate).
Volumistorage: upload, cache della licenza (license.json), controller custom, eventuali log su file. db-data: dati MySQL.

Questa tabella è il punto di incontro tra chi costruisce l'immagine e chi costruisce Chive CP: tenerla in un posto solo evita che i due lati divergano senza accorgersene. L'healthcheck sta nel compose perché altrimenti scheduler e worker, che non servono la porta 8080, risulterebbero sempre non sani; scheduler e worker aspettano l'app sana perché solo lei esegue le migrazioni; LOG_CHANNEL=stderr serve a leggere i log con docker logs. Il .env lo genera Chive CP alla creazione dell'istanza.

schema · chi avvia la creazione di un'istanza — amministratore vs richiesta demo rev. 2026-10-08

Amministratore

Oggi — priorità attuale

  1. Compila il modulo "Instance" nel pannello Filament (nome cliente, Data Plane su cui farla nascere, email del referente, scadenza della licenza, ecc.) — Chive CP propone già uno slug valido, modificabile
  2. Il record Instance nasce già "approvato" — è lui stesso l'amministratore a deciderlo
  3. Parte subito il job di creazione in coda — gli stessi comandi della sezione successiva
  4. Da qui in poi: stesso ciclo di vita di ogni istanza (check-in, aggiornamenti, backup)

Richiesta demo pubblica

Futuro — non ancora costruito

  1. Un visitatore compila il modulo "Preparami una demo" sulla landing page (nome azienda, non uno slug)
  2. La richiesta passa dal Gateway (Chive CP non ha listener pubblico) e crea un record Instance con stato "in attesa", con uno slug generato per intero da Chive CP
  3. L'amministratore la vede nel pannello e la approva con un click
  4. Da quel click in poi: lo stesso identico job di creazione della modalità amministratore — nessun meccanismo nuovo
  5. Da qui in poi: stesso ciclo di vita di ogni istanza (check-in, aggiornamenti, backup)

Le due modalità condividono lo stesso motore: cambia solo chi/cosa crea il record Instance e come viene validato prima di entrare in coda, non come l'istanza viene poi effettivamente creata. Per questo la richiesta demo pubblica si potrà aggiungere in un secondo momento senza toccare nulla di quanto già costruito per l'amministratore — è solo un secondo innesco verso lo stesso job. Il click di approvazione non è burocrazia fine a sé stessa: finché esiste, un modulo pubblico raggiungibile da chiunque non ha bisogno di anti-abuso sofisticato (rate limit aggressivi, verifica email, CAPTCHA) per restare sicuro, perché nessun container nasce davvero senza che un amministratore l'abbia guardato — un'approvazione automatica, se mai servirà, potrà arrivare più avanti come passo successivo, non come condizione per partire.

Lo slug (es. acme-corp) non è mai testo libero: finisce nel sottodominio pubblico, nel nome del progetto Docker (-p <slug> in ogni comando della sezione successiva) e nei percorsi di due macchine diverse — un carattere sbagliato lì dentro può rompere silenziosamente uno di questi usi. Per questo è Chive CP a generarlo, non chi scrive il modulo: lo calcola dal nome digitato (solo minuscolo, lettere/numeri/trattini), controlla che non sia già in uso e aggiunge da sola un suffisso (-2, -3...) se serve. Per l'amministratore è un suggerimento modificabile, ma sempre dentro queste regole; per la richiesta demo pubblica il visitatore non sceglie nulla — lo slug è generato per intero da Chive CP, e resta comunque correggibile dall'amministratore al momento dell'approvazione.

come funzionano i comandi verso il data plane rev. 2026-10-08

Tutte le operazioni sotto avvengono solo tramite un job in coda, mai come azione istantanea al click. Se un passaggio fallisce, si ferma lì — nessun tentativo automatico di ripeterlo. dataplane negli esempi è il nome di un context — vedi la sezione successiva per cosa significa.

Creazione istanza — fa partire i quattro container (db, app, scheduler, worker); scheduler e worker aspettano che l'app sia healthy. Le tabelle del database le prepara l'app stessa, all'avvio (le migrazioni girano ad ogni avvio del container, quindi anche dopo ogni aggiornamento): non c'è più un comando separato per questo.

docker --context dataplane compose -f /opt/chivecp/instances/<slug>/docker-compose.yml -p <slug> up -d

Verifica che sia pronta — guarda solo il container app (l'unico con healthcheck) e ripete questo controllo ogni 5 secondi finché non risulta healthy, o finché non scade un tempo massimo (300 secondi: la prima partenza misurata dura 65–145 secondi; un fallimento di migrazione resta starting fino a fine start_period, 240 s, quindi conviene leggere anche l'ultima riga di docker logs, [entrypoint] ERRORE, per accorgersene prima): non è un nuovo tentativo dopo un fallimento, è solo l'attesa che il normale avvio del container — migrazioni comprese — finisca. Il controllo vero è la pagina /health dell'app (risponde 200 se l'app e il database funzionano, 503 altrimenti); se il database non risolve, la risposta può metterci diversi secondi, quindi il controllo ha un suo timeout e lo tratta come "non sano".

docker --context dataplane inspect --format='{{.State.Health.Status}}' <slug>-app-1

Primo avvio dell'istanza — eseguito una sola volta, quando l'app risulta healthy. Crea i dati di base, il superadmin (senza password nota) e la riga di licenza, e stampa il link per impostare la password. La chiave e l'indirizzo del referente viaggiano solo in questo comando, non finiscono mai nel .env dell'istanza.

docker --context dataplane compose -p <slug> exec -T app php artisan instance:bootstrap \
  --admin-email=<email del referente> --license-key=<chiave>
// uscita: il link https://<slug>.<dominio>/admin/reset-password/<token>?email=...

Reinvia link — pulsante nel pannello. Genera un nuovo link (il precedente scade dopo 60 minuti) senza toccare nient'altro dell'istanza.

docker --context dataplane compose -p <slug> exec -T app php artisan instance:password-link \
  --admin-email=<email del referente>

Se la creazione fallisce (l'avvio dell'app non diventa mai healthy entro il tempo massimo — una migrazione fallita ne è la causa più probabile — oppure il primo avvio dell'istanza dà errore) — nessun rollback da fare, perché non esiste ancora nessun dato reale da proteggere: il job si limita a fermare i container (stessa azione di "Stop" qui sotto) e segna l'istanza come "creazione fallita", senza cancellare nulla in automatico. Se una migrazione fallisce, l'app non riprova da sola in ciclo (resta ferma, con l'errore nei log e la salute rossa), coerentemente con il principio di nessun tentativo automatico. Restano lì, ferme, finché l'amministratore non ispeziona i log per capire cosa non ha funzionato — solo a quel punto decide se eliminarla per sempre e riprovare da zero, o lasciarla così com'è.

Stop (reversibile) — ferma tutti e quattro i container (down agisce su tutti i servizi del compose), i dati salvati restano intatti.

docker --context dataplane compose -f /opt/chivecp/instances/<slug>/docker-compose.yml -p <slug> down

Eliminazione definitiva — stessa cosa su tutti e quattro i container, ma rimuove anche i dati salvati.

docker --context dataplane compose -f /opt/chivecp/instances/<slug>/docker-compose.yml -p <slug> down -v

Aggiornamento — Scheduler e worker sono processi di lunga durata: dopo un pull tengono in memoria il vecchio codice, quindi vanno ricreati. Sequenza: backup → si fermano scheduler e worker (niente job né pianificazioni durante la migrazione) → pull → si ricrea solo l'app, che esegue da sola le migrazioni prima di mettersi in ascolto → si attende healthy e lo smoke test → si ricreano scheduler e worker col nuovo codice. Il database resta sempre acceso. Se la migrazione o lo smoke test falliscono, scheduler e worker restano fermi e si segue il ripristino manuale descritto più avanti.

// 1. dopo il backup: ferma scheduler e worker
docker --context dataplane compose -f /opt/chivecp/instances/<slug>/docker-compose.yml -p <slug> stop scheduler worker
// 2. scarica la nuova versione (app, scheduler e worker usano la stessa immagine)
docker --context dataplane compose -f /opt/chivecp/instances/<slug>/docker-compose.yml -p <slug> pull app
// 3. ricrea solo l'app: le migrazioni girano all'avvio
docker --context dataplane compose -f /opt/chivecp/instances/<slug>/docker-compose.yml -p <slug> up -d --no-deps app
// 4. attende healthy (stesso controllo della creazione) + smoke test; solo se riusciti:
docker --context dataplane compose -f /opt/chivecp/instances/<slug>/docker-compose.yml -p <slug> up -d --no-deps scheduler worker

Backup — un backup è sempre una coppia di file con lo stesso nome e la stessa data e ora: il database e il volume storage (upload, controller custom del module builder, cache della licenza). Il database senza i suoi file non basta: i moduli custom sono scritti nel database ma i loro controller stanno in storage, quindi un ripristino parziale lascerebbe moduli rotti. Ogni file viene estratto, compresso e cifrato in un unico flusso continuo con la chiave dedicata a questa istanza, mai in chiaro su disco.

// 1. database
docker --context dataplane compose -p <slug> exec -T db sh -c 'mysqldump --single-transaction --add-drop-database --databases <slug>_db -u root -p"$MYSQL_ROOT_PASSWORD"' \
  | gzip \
  | openssl enc -aes-256-cbc -salt -pbkdf2 -pass env:BACKUP_ENCRYPTION_KEY \
  -out /tmp/<slug>_$(date +%F_%H%M%S).sql.gz.enc

// 2. storage: un container usa-e-getta (la stessa immagine dell'istanza, con il solo comando tar al posto dell'avvio normale) legge la cartella in sola lettura
docker --context dataplane run --rm --entrypoint tar -v /opt/customerhive/instances/<slug>/storage:/data:ro <immagine dell'istanza> \
  -C /data --exclude=./logs --exclude=./framework -czf - . \
  | openssl enc -aes-256-cbc -salt -pbkdf2 -pass env:BACKUP_ENCRYPTION_KEY \
  -out /tmp/<slug>_$(date +%F_%H%M%S).storage.tar.gz.enc

Regole del backup. (1) I due file portano lo stesso identico nome (data e ora comprese, non solo il giorno: un backup di sicurezza prima di un aggiornamento e uno pianificato nello stesso giorno non si devono sovrascrivere) e valgono solo insieme: se uno dei due non arriva allo storage offsite il job fallisce e il backup non conta, senza tentativi automatici. (2) Si esclude da storage ciò che si rigenera da solo (log e cache del framework). (3) Il dump e l'archivio sono presi a pochi secondi di distanza, non nello stesso istante: se in quell'intervallo un utente carica un file, il database e lo storage possono differire di quel solo file — accettato, perché fermare l'istanza a ogni backup costerebbe di più. (4) La chiave di cifratura è la stessa per i due file dell'istanza. (5) In questa v1 ogni backup è completo: se gli upload crescono molto, un archivio sempre completo diventa lento e pesante — un backup incrementale è un'evoluzione possibile, non una decisione presa.

Punto aperto — chi fa il backup di Chive CP stesso. Il database di Chive CP contiene le chiavi di cifratura di tutti i backup (cifrate con la sua APP_KEY), e sul suo disco stanno i .env delle istanze (con la loro APP_KEY) e la chiave SSH: se andasse perso senza copia, tutti i backup delle istanze diventerebbero illeggibili. Come e dove salvarli non è ancora deciso.

Ripristino — la stessa catena al contrario, per tornare a un backup precedente. Prima si fermano app, scheduler e worker (il database resta acceso); poi si riportano entrambi i file della coppia: il database e il volume storage, che viene svuotato e riempito di nuovo con il contenuto del backup (a tornare indietro devono essere anche i file, altrimenti restano controller più nuovi del database); infine si riavvia con il tag immagine coerente. Le cartelle escluse dal backup (log e cache) l'app le ricrea da sola all'avvio.

// 0. verifica d'integrità PRIMA di toccare qualcosa: il dump decifrato e decompresso deve finire con "-- Dump completed", l'archivio deve elencarsi senza errori
openssl enc -d -aes-256-cbc -pbkdf2 -pass env:BACKUP_ENCRYPTION_KEY -in <slug>_<data_ora>.sql.gz.enc | gunzip | tail -c 200 | grep -q -- "-- Dump completed"
openssl enc -d -aes-256-cbc -pbkdf2 -pass env:BACKUP_ENCRYPTION_KEY -in <slug>_<data_ora>.storage.tar.gz.enc | tar -tz > /dev/null

// 1. database (dopo aver fermato app, scheduler e worker)
openssl enc -d -aes-256-cbc -pbkdf2 -pass env:BACKUP_ENCRYPTION_KEY -in <slug>_<data_ora>.sql.gz.enc \
  | gunzip \
  | docker --context dataplane compose -p <slug> exec -T db sh -c 'mysql -u root -p"$MYSQL_ROOT_PASSWORD"'   # il dump contiene DROP/CREATE DATABASE: ricrea il database da zero

// 2. storage
openssl enc -d -aes-256-cbc -pbkdf2 -pass env:BACKUP_ENCRYPTION_KEY -in <slug>_<data_ora>.storage.tar.gz.enc \
  | docker --context dataplane run --rm -i --entrypoint sh -v /opt/customerhive/instances/<slug>/storage:/data <immagine dell'istanza> \
    -c 'find /data -mindepth 1 -delete && tar -xzf - -C /data'
schema · context Docker e Data Plane multipli rev. 2026-10-08

Cosa significa --context dataplane nei comandi appena visti, e come Chive CP gestisce più di un Data Plane.

Chive CP può gestire più Data Plane — alla creazione di un'istanza, l'amministratore sceglie da un elenco su quale farla nascere, e quella scelta resta scritta nel fascicolo dell'istanza per tutti i comandi futuri.

Cos'è di preciso un "context": è solo un nome comodo, salvato una volta su Chive CP, che tiene la corrispondenza "questo nome → questa macchina, raggiunta così". Non è il Data Plane in sé — è l'indicazione per trovarlo. Ogni Data Plane registrato ha il suo, distinto dagli altri: quando un comando dice --context dataplane-2, Chive CP va a guardare quella corrispondenza salvata e sa subito a quale macchina indirizzare l'ordine, senza doverlo cercare o indovinare ogni volta.

Registrazione di un nuovo Data Plane — fatta una volta sola, quando se ne aggiunge uno (non ad ogni istanza).

docker context create dataplane-2 --docker "host=ssh://deploy@10.0.4.12"

Elenco dei Data Plane registrati — è la lista da cui l'amministratore sceglie alla creazione di un'istanza.

docker context ls

Il file docker-compose.yml (e il .env a fianco) non lasciano mai Chive CP — nessun trasferimento verso il Data Plane. Chive CP li legge in locale e li trasforma in istruzioni già complete ("crea un container con queste caratteristiche, con queste variabili già dentro") che manda al Docker del Data Plane attraverso il context: è quello a eseguirle davvero, senza aver mai bisogno di una sua copia dei file. I due file restano sul disco di Chive CP per tutta la vita dell'istanza — servono di nuovo a ogni aggiornamento futuro — e vengono cancellati solo quando elimini l'istanza per sempre. L'unica accortezza: le cartelle da montare (storage — upload, cache della licenza, controller custom — e dati del database) vanno scritte nel file come percorsi validi sul Data Plane.

schema · come nasce la licenza e il primo accesso — managed vs self-hosted rev. 2026-10-08

Managed

Istanza su infrastruttura nostra — v1

  1. Chive CP crea la licenza nel proprio database (è lo stesso applicativo delle licenze): dominio e path esatti dell'istanza, limiti di tenant e utenti, moduli. Ottiene la chiave
  2. Chive CP fa partire i quattro container (SSH sul Data Plane). All'avvio l'app esegue da sola le migrazioni e diventa healthy
  3. Solo allora Chive CP lancia un comando dentro il container, instance:bootstrap: crea i dati di base, il superadmin con una password che nessuno conosce, inserisce la chiave nella tabella license e stampa il link per impostare la password
  4. Chive CP invia quel link al referente del cliente con la propria posta (l'istanza non ha ancora la posta configurata) e non lo conserva
  5. Il cliente imposta la sua password; al primo login e poi ogni ora l'app scarica la licenza. Il primo check-in arrivato al Gateway segna l'istanza "attiva"

Self-hosted

Istanza su infrastruttura del cliente — rimandato, non fa parte della v1

  1. Chive CP genera la licenza per il dominio (stessa funzione)
  2. La chiave e il contatto del referente finiscono nel file .env del pacchetto
  3. Il pacchetto va all'IT del cliente, che lo scarica e fa partire il container
  4. Qui non c'è nessun Chive CP a lanciare un comando: lo stesso instance:bootstrap dovrà partire da solo al primo avvio leggendo il .env — ancora da progettare
  5. Da qui in poi: check-in orario verso il Gateway — l'unico segnale che abbiamo

Cosa esiste già e cosa no. Oggi l'app non legge nessuna chiave dal .env: l'unico modo per registrarla è la schermata "Ho già una licenza" nel browser. Il comando instance:bootstrap è quindi nuovo: salta quella schermata e inserisce la riga nella tabella license direttamente — senza nessuna chiamata di rete, perché al primo login l'app scarica già da sola il resto della licenza (lo fa ad ogni login e poi ogni ora). Per l'istanza Managed la chiave non finisce nemmeno nel .env: sta solo nel database di Chive CP e in quello dell'istanza. Il comando si rifiuta di girare se l'istanza è già stata inizializzata.

Il link per impostare la password. Non esiste nessuna password iniziale da consegnare: l'app ha già il meccanismo del "password dimenticata" (token monouso, stessa policy: almeno 12 caratteri, nessuna password comune), e instance:bootstrap lo riusa. Il link vale 60 minuti come ogni reset. Se il cliente non fa in tempo, l'amministratore preme "Reinvia link" nel pannello di Chive CP: parte un nuovo comando che genera un nuovo token e una nuova email. Il link è un segreto in transito: Chive CP lo legge dall'uscita del comando, lo manda per email e non lo scrive né nei log né nel database.

Come si crea la licenza di un'istanza Managed. (1) Il domain è l'host completo dell'istanza, <slug>.<dominio base>, identico al APP_DOMAIN scritto nel suo .env. (2) Il path non ha un significato fisico in Docker: si usa lo slug, lo stesso valore in licenza e in APP_PATH. (3) Il controllo dell'IP è disattivato (vedi sopra). (4) La scadenza va scelta sempre in modo esplicito — per contratto, o in giorni per una demo — perché il valore di default del server è 30 giorni; Chive CP ha un'azione "Rinnova", perché una licenza scaduta blocca il login dell'intera istanza. Il rinnovo basta: l'istanza conserva la chiave e il login riparte da solo. Se in via eccezionale la chiave cambia (licenza ricreata) o va persa, non c'è un comando dedicato: Chive CP la re-registra con una POST a /admin/activate-existing-license (campo license_key, senza login) oppure con un UPDATE della tabella license. (5) Quando un'istanza viene eliminata per sempre, Chive CP revoca anche la sua licenza: il server rifiuta una seconda licenza per lo stesso dominio, quindi senza revoca lo slug non si potrebbe riutilizzare.

Il "check-in orario" non è l'unico momento di validazione: la licenza viene controllata anche ad ogni login e quando si crea un nuovo tenant o utente dentro l'istanza — questo schema si concentra sul check-in periodico perché è quello rilevante per sapere se un'istanza è ancora viva e su che versione gira.

├── .env                                LICENSE_KEY, APP_KEY, credenziali DB — già compilato

schema · pipeline di build e rilascio rev. 2026-10-08
Gateway Chive CP Istanza aggiornata Fasi della pipeline

Il ramo sinistro (dev) parte da solo a ogni push. Il ramo destro (release) parte solo quando tu crei un tag Git — nessuna immagine semver arriva mai a staging o a un cliente senza un'azione esplicita. In entrambi i casi la pipeline (GitHub Actions, che gira fuori dalla nostra infrastruttura) non può chiamare Chive CP direttamente — non ha alcun listener pubblico — quindi passa sempre dal Gateway, con lo stesso token di servizio usato per il webhook di dev. Questo valore è quello con cui Chive CP confronta la versione in uso su ogni istanza per segnalare chi è rimasto indietro: per le managed lo sa già da sé — è stata lei a eseguire l'ultimo aggiornamento, quindi il proprio fascicolo dice già che tag gira; per le self-hosted invece il check-in è l'unica fonte, perché è il cliente a decidere se e quando applicare l'aggiornamento, e Chive CP non ha altra visibilità su cosa sia realmente in esecuzione.

Come la pipeline chiama davvero il webhook — non c'è nulla di speciale: GitHub Actions esegue la pipeline su una macchina temporanea con accesso a internet come qualunque altra, quindi l'ultimo passo del job (subito dopo il push riuscito dell'immagine) è solo una richiesta HTTP in uscita, la stessa cosa che farebbe un browser.

curl -X POST https://gateway.thecustomerhive.com/ci/webhook \
  -H "Authorization: Bearer $CI_WEBHOOK_TOKEN" \
  -d '{"tag":"dev-a1b2c3d"}'

Il registry. Docker Hub privato, piano gratuito, con un solo repository che contiene tutti i tag (dev-latest, dev-<sha>, vX.Y.Z). Servono due token nuovi: uno di scrittura, nei "Secrets" di GitHub Actions, usato dalla pipeline per pubblicare; uno di sola lettura, con cui si fa docker login una volta su ogni Data Plane, usato dal pull. Per ora solo istanze Managed: il self-hosted è rimandato.

Il Gateway riceve questa richiesta come una qualsiasi altra sulla sua rotta pubblica POST /ci/webhook — non sa né gli interessa che ad averla mandata sia stato uno script invece di una persona. Il token ($CI_WEBHOOK_TOKEN) non è mai scritto nel codice della pipeline: vive una volta sola nei "Secrets" di GitHub Actions, e viene inserito automaticamente come variabile d'ambiente solo durante l'esecuzione — così non compare mai in chiaro nel repository.

schema · aggiornamento istanza e ripristino da backup rev. 2026-10-08
Chive CP Fallimento Istanza (esito) Fasi del processo / azioni manuali

La sequenza. Scheduler e worker sono processi di lunga durata: dopo un pull tengono il vecchio codice in memoria, quindi vanno ricreati; si fermano prima della migrazione perché nessun job o pianificazione deve girare mentre lo schema del database cambia, e si riavviano solo quando app e smoke test hanno dato esito positivo. Se qualcosa fallisce restano fermi. Il pull che fallisce è il caso più innocuo: succede prima che il container dell'app venga toccato, quindi quello vecchio sta ancora girando, intatto (restano da riaccendere solo scheduler e worker, già fermati prima del pull: il job li riavvia col codice che già avevano) — non serve nessun ripristino, basta segnare il tentativo come fallito e riprovare quando vuoi. Migrazioni e smoke test falliti finiscono invece nello stesso percorso di ripristino, anche se solo la migrazione cambia davvero lo schema del database: tenerli uniti evita di dover costruire e verificare due percorsi diversi, e riporta sempre a una combinazione immagine+database di cui sai già che funzionano insieme. Il ripristino non usa "l'immagine precedente" da sola: applica di nuovo il database del backup pre-aggiornamento, perché MySQL non annulla da solo una modifica di struttura a metà, insieme al volume storage della stessa coppia (così database e file, controller custom compresi, tornano allo stesso momento) — poi riporta anche il tag immagine coerente con quei dati. Questo ramo non parte mai da solo: dopo un aggiornamento fallito tutto si ferma e aspetta — solo l'avvio del ripristino richiede una tua azione esplicita (ispezione + conferma), poi Chive CP esegue il resto in automatico, come un job qualunque. La conferma richiede di digitare lo slug dell'istanza, non un semplice "Sì": un click per abitudine è facile su un "Sei sicuro?", mentre scrivere il nome esatto ti costringe a verificare consapevolmente su quale istanza stai per sovrascrivere il database — l'ultima rete contro un click sulla riga sbagliata, prima che diventi irreversibile.

Solo dati, nessun file di configurazione: docker-compose.yml e .env non stanno qui — restano su Chive CP (vedi sotto) e non vengono mai trasferiti, come già spiegato. Nessun backup qui: se il Data Plane viene compromesso o perso, non c'è nulla di cifrato da recuperare su questa macchina — solo container e dati correnti.

/opt/chivecp/                            sul Control Plane
└── instances/
    ├── dev/
    │   ├── docker-compose.yml               4 servizi: db, app, scheduler, worker — letto da Chive CP, mai inviato
    │   └── .env                             APP_KEY, APP_DOMAIN, credenziali DB... (senza chiave di licenza)
    ├── staging/
    └── <slug-cliente>/

Il docker-compose.yml definisce i quattro servizi di ogni istanza (db, app, scheduler, worker), con i volumi storage e db-data e le variabili elencate nel contratto dell'immagine; il .env a fianco lo genera Chive CP alla creazione. La chiave di licenza di un'istanza Managed non è nel .env.

Ogni cartella qui rispecchia una in instances/ sul Data Plane, stesso slug — ma il contenuto è complementare: qui la configurazione, là i dati. Restano entrambe finché l'istanza esiste, e vengono rimosse insieme solo con l'eliminazione definitiva.

storage offsite/                          non su Chive CP, non sul Data Plane
└── backups/
    └── <slug-cliente>/
        ├── <slug-cliente>_2026-09-17_031500.sql.gz.enc           database, già cifrato prima di lasciare Chive CP
        └── <slug-cliente>_2026-09-17_031500.storage.tar.gz.enc   storage (upload, controller custom), stessa coppia

Chive CP non trattiene una copia locale del backup: cifra il dump e l'archivio appena arrivano e li inoltra subito allo storage offsite, senza conservarne un'altra copia sul proprio disco — meno dati sensibili fermi su una singola macchina. Chiusura (reversibile): il container si ferma, instances/<slug>/ resta intatta sul Data Plane. Eliminazione definitiva: quella cartella viene rimossa dal Data Plane e da Chive CP, ma il backup offsite resta (database e storage, sempre in coppia) — è l'ultima rete di sicurezza anche dopo la cancellazione, e sopravvive pure a un problema sul Data Plane o sul Control Plane, perché vive su una terza destinazione.
