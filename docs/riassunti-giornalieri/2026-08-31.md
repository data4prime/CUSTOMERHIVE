# 2026-08-31 — Tre bug reali di licensing/login trovati dopo la riattivazione dei controlli

- **Login/logout rotti nei test**: `canLicenseLogin()`, chiamato in testa a
  `postLogin()`, blocca sempre il login senza una licenza valida in DB — nel
  DB di test (sempre vuoto) questo rompeva `LoginTest` (3 test) e
  `LogoutTest`, che si basavano sul vecchio bypass
  `LICENSE-CHECK-DISABLED-DEV` rimosso il 26/08. Aggiunto un bypass
  esplicito solo per l'ambiente `testing`, non raggiungibile in produzione.
- **Campo Agent AI visibile a torto** su voci di menu di tipo Route/URL/
  Controller & Method: nel ramo JS di default mancava il nascondimento di
  `#form-group-chat_ai`, già presente negli altri rami. Visibile aprendo in
  edit una voce di menu di tipo Route.
- **Crash su risposta del license server senza la busta `{success,...}`
  attesa**: `ConnectorService::getAccessToken()` indicizzava
  `$data['success']` senza controllare che la chiave esistesse — una
  risposta 200 in formato inatteso (visto su
  `dev.thecustomerhive.com/admin/activate-existing-license`) generava un
  errore non gestito invece dell'`AuthException` prevista. Siccome
  quell'eccezione bypassava anche il cleanup in
  `postActivateExistingLicense()`, la riga inserita in `license` restava
  orfana e faceva ripetere lo stesso crash a ogni login successivo
  (`canLicenseLogin()` chiama lo stesso codice). Aggiunto anche un catch
  esplicito in `canLicenseLogin()` così un errore/risposta malformata del
  license server blocca il login col messaggio esistente invece di un 500.
