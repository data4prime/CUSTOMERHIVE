# 2026-09-02 — Giro di sicurezza su API/Settings/Statistic Builder, pianificato lo scenario di test manuale

- **RCE nel modulo API Generator, corretta** (`ApiCustomController::postSaveApiCustom()`,
  usato anche da `CRUDBooster::generateAPI()`): `$table_name`/`$permalink`/
  `$method_type` finivano incollati grezzi dentro literal PHP a doppi
  apici nel sorgente di un controller scritto su disco e subito
  autoloaded — una virgoletta nel valore bastava per iniettare PHP
  arbitrario, senza nemmeno un check `isSuperadmin()` a proteggere l'endpoint
  (gap di autorizzazione rimandato, segnalato in `docs/refactoring/README.md`).
  Corretto con `var_export()` (literal a singoli apici) sia in generazione
  che in modifica, più sanificazione di `$controllerName` contro path
  traversal. `tests/Feature/ApiCustomCrudTest.php` (19 test) copre la
  regressione (`docs/refactoring/065`).
- **Crash in `ApiController::execute_api()`**: `$row_api` veniva
  dereferenziato prima del controllo "riga esistente" più avanti nello
  stesso metodo — un permalink senza corrispondenza in `cms_apicustom`
  dava 500 invece del messaggio d'errore già previsto. `ApiExecuteTest`
  (5 test, comportamento a runtime, non la generazione) ha scoperto anche
  che `detail` fa il merge dei campi al livello superiore della risposta,
  a differenza di `list` (`docs/refactoring/066`).
- **3 bug reali nel modulo Settings**: `CRUDBooster::valid()` chiamava
  `exit()` invece di tornare la response (stesso refactor già fatto altrove
  il giorno prima, mai applicato qui); cancellare una riga di
  `cms_settings` (niente `deleted_at`, quindi DELETE fisica) non invalidava
  la cache (`Cache::forever()`) né puliva l'eventuale file caricato —
  aggiunto un `hook_before_delete()` che riusa la logica già corretta di
  `getDeleteFileSetting()`. `SettingsCrudTest` (27 test), suite completa
  118/118 (`docs/refactoring/064`).
- **SQL arbitrario nel modulo Statistic Builder, corretto**:
  `postSaveComponent()` — unico punto di scrittura della config dei widget,
  eseguita letteralmente via `DB::select()` da 6 dei 10 tipi di widget in
  fase di rendering — non aveva alcun controllo di privilegio, a differenza
  degli altri metodi dello stesso controller: qualunque utente autenticato
  poteva scrivere ed eseguire SQL arbitrario su qualsiasi dashboard
  esistente. Aggiunto lo stesso check `isSuperadmin()` già usato altrove,
  *senza* toccare `getViewComponent()`/`getListComponent()` (usati anche
  dalla normale visualizzazione delle dashboard, non solo dall'editor).
  Verificato e scartato come falso allarme un possibile path traversal via
  `component_name`. `StatisticBuilderCrudTest` (14 test), suite completa
  157/157 (`docs/refactoring/067`).
- **Pianificato lo scenario per il giro di test manuale** su
  `dev.thecustomerhive.com` (doppio scopo QA+demo): 3 tenant asimmetrici
  (Novara Energia/Bluewave Logistics/Portosole SpA) con gruppi, ruoli
  granulari, scadenze utente, Module Generator (Contratti+Fatture
  collegate), Statistic Builder e API Generator — costruito sui meccanismi
  reali verificati nel codice (visibilità menu per tenant/gruppo,
  fallback `home.blade.php`), non a caso. Qlik/Chat AI esclusi per ora.
  Discussa anche una variante "Scenario B" (un solo cliente, i tenant
  rappresentano i reparti interni, per mettere sotto stress le dashboard
  condivise tra più reparti). Salvato in `docs/piano-testing-manuale.md`.
