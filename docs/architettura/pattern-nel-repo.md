# Catalogo dei pattern già usati nel repo

> Letto da `/architect` e `ch-architect-analyst`. Serve a proporre struttura
> **coerente con quella esistente**, non da manuale. Quando nasce un nuovo
> pattern di riferimento (es. la prima Action ben fatta), aggiungilo qui.

## Pattern con un esempio di riferimento

| Pattern | Esempio nel repo | Quando imitarlo |
|---|---|---|
| **Service + Strategy + Factory** (integrazione esterna) | `app/Services/QlikSync/` — `QlikDriver` (interfaccia), `OnPremQlikDriver`/`SaasQlikDriver` (strategie), `QlikDriverFactory`, `QlikSyncService` (orchestrazione), `QlikSyncRollback`, `QlikSyncException` | Più varianti di un sistema esterno dietro la stessa operazione. |
| **Service semplice per una chiamata esterna, con lettura della risposta testabile** (doc 331) | `app/Services/ChatAI/ChatAIClient.php` (`send()` + `interpret()` pubblica) usato dal metodo **privato** `relayToAgent()` di `AdminChatAIController` | Una sola variante di un sistema esterno (niente Strategy/Factory) chiamato da più punti di un controller. Il servizio non legge sessione/richiesta/`CRUDBooster`: riceve tutto per parametro e il controller decide sessione, storico, echo. Separare la lettura della risposta dalla chiamata cURL (non simulabile nei test) per provare i rami senza rete. **Niente type hint nuovi** rispetto al codice di origine. Il metodo di appoggio nel controller deve essere `private`: un metodo pubblico diventa una rotta. |
| **Service per un'operazione di sistema, con eccezione di dominio** (doc 334) | `app/Services/ModuleGenerator/ModuleExporter` (`export($id)`), `ModuleImporter` (`import(string $contents)`), `ModuleTransferException` (messaggio già tradotto + `type()` `warning`/`danger`) usati da `ModulsController::getExport()`/`postImport()` | Blocco di logica isolato dentro un controller di sistema, con molti rami di rifiuto. Il service non legge sessione né richiesta e lancia l'eccezione; il controller tiene permesso, file/HTTP e **i redirect identici a oggi per ciascun endpoint** (anche se due endpoint rifiutano in modo diverso). Codice dei privati spostato identico (niente type hint, cast o transazioni nuovi, stesso ordine dei controlli). Se un metodo privato serve anche altrove (qui `layoutPlaceableFields` per il wizard), aggiungere un metodo statico additivo su un helper e lasciare nel controller un wrapper di una riga. Si istanzia con `new`. Prima i test di caratterizzazione sul codice vecchio. |
| **Job in coda** | `app/Jobs/SyncQlikRunJob.php`, `SendTemplateEmailJob.php` | Lavoro lento o ritentabile; il controller avvia (`HandlesQlikSyncStart`) e non attende. |
| **Trait per comportamento condiviso di controller** | `Controllers/System/Concerns/HandlesQlikSyncStart.php` | Logica comune a 2+ controller di sistema, senza toccare la gerarchia `CBController`. |
| **Action (un'operazione, un solo `handle()`)** | `app/Actions/Menus/AssignDefaultMenuTenant.php`, `AssignDefaultMenuGroup.php`, `app/Actions/Groups/AddTenantToGroup.php` (doc 322), `app/Actions/ApiTokens/GenerateApiToken.php` (doc 328: prima Action su un modello Sanctum, con parametri semplici più `User`, restituisce `NewAccessToken`; il controller tiene redirect di errore, `insertLog` e vista; si istanzia con `new`, non con `app()`), `app/Actions/ChatAI/` (doc 330: `SetPrimaryChatAIConf`, `Allow*`/`Revoke*` per tenant e gruppo; il controller tiene permesso, `is_int`/`exists`, `safeRedirectTarget` e redirect; gli hook di `CBController` restano e chiamano l'Action; `Allow*` restano count-poi-insert; per un modello `SoftDeletes` l'Action usa la query Eloquent, non `DB::table()`) | Operazione di scrittura che oggi vive in un modello o in un controller. Riceve gli id come parametri (niente `UserHelper`/sessione/richiesta dentro), niente stato. Il vecchio metodo del modello resta come wrapper sottile per i controller dei clienti. Prima di sostituire i punti di chiamata, cercare i chiamanti con tokensave e controllare i tipi (un `int` può cambiare il valore salvato). |
| **Local scope sul modello (mai global)** | `Menu::activeDashboard()`, `Menu::qlikItemContent($id)`, `UsersGroup::ofUser($id)`, `UsersGroup::ofGroup($id)` (doc 322) | Stessa condizione identica ripetuta in 2+ punti. Il test confronta `toSql()`/bindings con la query esplicita. Non per `ModuleHelper::can_*` (permessi per tenant) né per il login. |
| **Relazione Eloquent additiva con nome nuovo** | `Menu::assignedTenants()`, `User::tenantRecord()/primaryGroupRecord()/memberGroups()`, `QlikItem::allowedGroupRecords()` (doc 319) | Si aggiunge accanto al metodo esistente senza sostituirlo se il metodo ha una semantica diversa (soft-deleted inclusi, ordine). Il nome non deve coincidere con una colonna. |
| **Trait `Concerns` per i controller di sistema (uso condiviso)** | `Controllers/System/Concerns/SafeRedirectTarget.php` (usato da `AdminQlikItemsController`, `AdminChatAIController` e, dal doc 326, dagli `add_*` di `AdminGroupsController`, `AdminCmsUsersController`, `AdminTenantsController`) | Comportamento identico in 2+ controller di sistema: estrarlo invece di copiarlo. Un filtro di sicurezza condiviso si corregge nel trait (si propaga a tutti), con il test dei valori malformati. |
| **Form Request (pilota, doc 327)** | `app/Http/Requests/ApiTokens/StoreApiTokenRequest.php` + `ApiTokensController::postAddSave()` | Validazione/permesso in linea in un metodo di controller di sistema. `authorize()` replica il vecchio controllo e `failedAuthorization()` rilancia lo stesso redirect (niente 403); `rules()` identiche. **Dentro un override di `CBController` non si inietta dalla firma** (il padre non ha parametri: errore fatale, o `null` se opzionale): si usa il metodo statico `validateCurrent()` (createFrom + setContainer + setRedirector + validateResolved). **Mai `app(FormRequest::class)`** nel perimetro Larastan: lo esegue davvero durante l'analisi (ADR A14). Dal secondo Form Request estrarre `validateCurrent()` in un trait **se serve negli override**. **Metodi custom che NON sono override di `CBController`** (es. `send_message`/`send_message_agent` di `AdminChatAIController`, rotte esplicite in `routes/web.php`): il Form Request si **inietta dalla firma** e non serve `validateCurrent()` (doc 333: `app/Http/Requests/ChatAI/Send*Request`). Prima verificare che nulla di `CBController` li invochi senza container (`routeController` registra solo `get*`/`post*`). Se il metodo risponde con `echo` e un rifiuto diventa una `Response`, i test che leggono solo il buffer vanno adattati. Per un endpoint AJAX il rifiuto è un `HttpResponseException` con JSON, non il redirect di `CRUDBooster::redirect()`. **Più Form Request con lo stesso rifiuto JSON** (doc 335: `app/Http/Requests/Profile/*` per i `postProfile*` di `AdminCmsUsersController`): il rifiuto va in un trait condiviso (`Concerns/RespondsWithProfileJson`: `failedAuthorization()` 403 e `failedValidation()` 422, stesso JSON di prima); `authorize()` replica la condizione in linea senza semplificarla. I metodi auto-instradati (`post*` di `routeController`) accettano il Form Request nella firma: le rotte hanno wildcard fisse. Un metodo in cui un controllo (es. rate limit 429) precede la validazione **non** si converte: l'ordine cambierebbe. |
| **Tabelle di autorizzazione dedicate per tipo di oggetto** | `chatai_groups_allowed` / `chatai_tenants_allowed` (ADR A12), pivot `ChatAIGroupAllowed`/`ChatAITenantAllowed`, relazioni `ChatAIConf::allowedGroupRecords()/allowedTenantRecords()` | Nuovo tipo di oggetto da autorizzare per gruppo/tenant: non riusare `items_allowed`/`tenants_allowed` di Qlik. Prima relazione `belongsToMany` del repo. |
| **Comando Artisan con trait di supporto** | `Console/Commands/Concerns/InstanceCommandSupport.php` | Operazioni di istanza/CLI. |
| **Helper statico di dominio piccolo** | `MailSettings`, `PasswordPolicy`, `TenantHelper` | Logica senza stato. Ok per ciò che esiste già; per codice **nuovo** preferire una classe iniettabile. |
| **Dataset/registry dichiarativo** | `app/Dashboards/DashboardDatasetRegistry` + `DatasetAccessScope` | Catalogo di sorgenti con scope di accesso esplicito. Nota: `DatasetAccessScope` è l'unico oggetto "scope di accesso" del repo, utile come modello per il tenant. |
| **Alias di compatibilità** | `app/Support/legacy_crudbooster_aliases.php` | Mai rimuovere finché ogni cliente non è migrato. |
| **Spostamento di un modello in `App\Models` con alias e migration** (doc 336) | `App\Models\User` + `class_alias(\App\Models\User::class, 'App\User')` + migration `update_tokenable_type_for_user_model` | Un modello alla volta. Prima i test di caratterizzazione (vecchio nome ancora valido, nome nuovo, alias, guard `config/auth.php`); copiare il file con solo namespace e `use` dei modelli ancora in `App\`; alias nello stesso file degli altri; migration (con `down()`) per le colonne polimorfiche che salvano il nome (`personal_access_tokens`, altre da verificare sul DB); poi aggiornare i riferimenti del repo con **Edit o uno script `sed` su file, mai `sed` inline con backslash**, e verificare con una ricerca indipendente. |
| **Feature flag** | `MODULE_GENERATOR_WIZARD_V2`, `CH_UI_V2` | Cambi visibili da introdurre e poter spegnere. |

## Pattern assenti (introdurli è un fatto nuovo, da discutere)

Policy/Gate, Event+Listener di dominio, Observer, API Resource, scope
Eloquent globale per tenant (Action e Form Request esistono ora con un solo
esempio pilota ciascuno, vedi tabella). Quando se ne propone uno
**per la prima volta**, la proposta deve includere: l'unico esempio pilota,
dove vivrà la cartella (`app/Actions/`, `app/Http/Requests/`,
`app/Policies/`), e una nota qui dopo l'implementazione.

## Anti-pattern da NON proporre in questo repo

- Rinominare/spostare `CBController`, `CRUDBooster::`, `crudbooster::`, tabelle
  `cms_*`, alias legacy, proprietà `$this->form|col|…` e hook `hook_*`.
- Rimuovere campi da `$this->form` (usa `hide_form`).
- "Spezzare" i `cbInit()` lunghi: sono configurazione dichiarativa.
- Repository "per principio" sopra Eloquent.
- Service/Manager "contenitore" generici (`ApplicationService`, `HelperManager`).
- Riscritture ampie o refactoring non behavior-preserving: tutto a batch
  piccoli, strangler fig.
- Pint o Larastan sull'intero repo (solo sui file toccati / sul perimetro
  indicato in `.claude/rules/`).
- Proposte che dipendono da una copertura test che non esiste, senza prima
  indicare il test di caratterizzazione.
